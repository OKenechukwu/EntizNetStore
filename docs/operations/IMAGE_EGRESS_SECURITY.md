# EntizNetStore image egress security

Last reviewed: **2026-08-31**

## Purpose

Next.js image optimization is a server-side fetch surface. A broad `remotePatterns` rule can turn an otherwise harmless persisted image URL into server-originated network access. EntizNetStore therefore treats every dynamic image URL as untrusted input and keeps both the optimizer and browser image egress on an explicit allowlist.

## Canonical production boundary

Dynamic remote images are allowed only when all of the following are true:

- the origin is the configured EntizNetStore Supabase project;
- managed Supabase uses HTTPS; local HTTP is accepted only for the isolated loopback development/CI stack;
- no URL credentials are present;
- the path is under the Supabase public-object route;
- the bucket is exactly `product-media` or `seller-branding`;
- path traversal, backslash and NUL encodings are rejected.

The Next image optimizer mirrors the same network boundary with exactly two remote path patterns:

- `/storage/v1/object/public/product-media/**`
- `/storage/v1/object/public/seller-branding/**`

No wildcard hostnames are permitted. Private `kyc-documents`, `message-attachments`, `upload-quarantine`, signed-object routes, Auth/API routes and arbitrary external hosts are not optimizer destinations.

## Server-side fetch defenses

`next.config.js` keeps these controls enabled:

- `maximumRedirects: 0` — an allowed URL cannot redirect the optimizer to a second destination;
- `dangerouslyAllowLocalIP: false` — remote optimization must not opt into local/private network access;
- `dangerouslyAllowSVG: false` — untrusted remote SVG processing is not enabled;
- `contentDispositionType: 'attachment'` — direct optimizer responses retain the safer disposition baseline;
- exact Supabase host + approved public-bucket paths only.

The live regression probes `/_next/image` and requires HTTP 400 for an arbitrary HTTPS origin, the application loopback origin, Supabase non-storage routes and private bucket paths. The test deliberately verifies rejection before any remote image is accepted.

## Browser image egress

The production Content-Security-Policy no longer uses a bare `https:` source for `img-src`. Browser images may load from:

- `'self'`;
- `data:` and `blob:` for bounded local UI use;
- the exact configured Supabase origin when it passes the canonical binding validation.

This prevents a compromised/persisted image URL from silently becoming an arbitrary third-party tracking request even when the browser would otherwise render a raw image element.

## Application media validation

`lib/storage/publicMedia.ts` is the client/server-safe canonical renderer check for persisted media references. It accepts only approved repository-local media namespaces or canonical Supabase public image objects. Product cards fall back to a local image when persisted media is invalid. Product galleries filter invalid references instead of handing them to `next/image` or a raw `<img>` element.

This rendering control complements, rather than replaces, upload authority. Product media is already accepted server-side only after ownership, Supabase origin/path, size, real JPEG/PNG/WebP signature and quarantine/scanner/promotion controls pass. Seller branding is likewise generated by the trusted upload pipeline rather than by accepting arbitrary remote URLs.

## CI and release verification

`.github/workflows/image-egress.yml` is a dedicated release gate. It:

1. runs the repository image-egress foundation verifier;
2. runs canonical public-media source tests;
3. reloads and tests `next.config.js` across managed Supabase, loopback and hostile/malformed configuration cases;
4. builds the production application;
5. boots the real Next server and runs the live optimizer rejection probes.

The general production-foundation command also freezes the existence of this security boundary so it cannot disappear unnoticed from ordinary CI.

After promotion, verify the canonical production response CSP has no bare `https:` token in `img-src`, contains only the expected Supabase image origin, and that a deliberately unapproved `/_next/image` URL is rejected with HTTP 400. Review runtime error/fatal logs after the deployment.

## Adding a future CDN or image provider

A future image/CDN origin is not added by broadening to `https:` or `hostname: '**'`. The change must instead:

1. document why the provider is required and what objects it serves;
2. add the smallest exact HTTPS hostname and pathname pattern possible;
3. prohibit redirects unless a reviewed provider contract makes them unavoidable;
4. ensure private/internal IP destinations remain unreachable;
5. update `isTrustedPublicMediaSource` or introduce a provider-specific validator;
6. update CSP with the exact image origin only;
7. add positive and negative unit/config/live regression cases;
8. pass the complete CI, browser/authorization gates and production release verification.

Do not treat CSP as authorization. Storage ownership, RLS and trusted upload/promotion remain authoritative.

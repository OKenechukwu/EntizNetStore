# ESLint quality baseline and non-regression gate

Last reviewed: **2026-08-25**

## Purpose

EntizNetStore now runs the real Next.js/React/TypeScript ESLint rule set in CI. This is a production quality gate, not a claim that legacy application code is already lint-clean.

The repository inherited substantial lint debt before lint was made executable under the current Next.js toolchain. Rewriting hundreds of findings in one launch-hardening change would create unnecessary commerce/auth/UI regression risk. The production-safe approach is therefore a measured ratchet:

1. keep the full rule set enabled;
2. record the exact inherited finding categories in `eslint-baseline.json`;
3. fail CI if any file/rule/message category increases;
4. permanently reject fatal parser/configuration failures and zero-tolerance Hook violations even if a baseline is regenerated;
5. reduce the committed baseline as code is safely cleaned module by module;
6. retain `npm run lint:strict` as the end-state zero-finding target.

## Toolchain contract

- Next.js: `16.3.1` compatible range from the lockfile/manifests;
- Node.js: repository contract `>=22 <23`;
- ESLint configuration: flat `eslint.config.mjs`;
- Next rules: `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript`;
- ESLint runtime: pinned to `9.39.5` while the installed Next.js lint plugin stack remains incompatible with ESLint 10;
- canonical CI command: `npm run lint`;
- strict cleanup command: `npm run lint:strict`.

The initial attempt with ESLint 10.8.1 was not merely noisy: the installed Next/React lint plugin crashed during execution. The root ESLint dependency was therefore moved to the compatible ESLint 9 line and `package-lock.json` was regenerated by npm itself on Node 22 rather than edited manually.

This compatibility pin is temporary technical debt. Re-evaluate and move to the supported newer ESLint major when the installed Next.js lint stack supports it; do not force ESLint 10 while the plugin contract is incompatible.

## Current measured baseline

The final baseline generated on 2026-08-25 contains:

- **363 total findings**;
- **266 errors**;
- **97 warnings**.

That is already lower than the first successful full-rule run, which exposed 367 findings. Before freezing the baseline we fixed a direct React-state mutation in `components/products/ProductForm.tsx` and removed two stale lint-disable directives.

`eslint-baseline.json` stores counts by normalized `file::ruleId::messageId`. It intentionally does not store source snippets or customer data.

## What CI permits

A finding already represented in the committed baseline may remain while its owning module is being migrated, provided its category count does not increase.

A category count may decrease without requiring an immediate baseline rewrite. The lint command reports the improvement. Baseline updates should be committed intentionally after meaningful cleanup so the ratchet is tightened rather than loosened.

## What CI never permits

`scripts/lint-with-baseline.mjs` rejects all of the following regardless of the committed baseline:

- ESLint configuration/execution failure before results are produced;
- fatal parser/configuration findings;
- `react-hooks/rules-of-hooks` findings;
- `react-hooks/set-state-in-render` findings;
- any new finding category absent from the baseline;
- any increase in an existing file/rule/message category.

The baseline writer itself refuses to generate a snapshot while a fatal or zero-tolerance finding exists. This prevents a broken parser/configuration or invalid Hook call from being waived by simply regenerating the file.

## Baseline maintenance rule

Do **not** regenerate `eslint-baseline.json` simply because CI fails.

When CI reports a regression:

1. inspect the new/increased finding;
2. fix the code when it is a real regression;
3. only change the baseline when an intentional, reviewed rule/toolchain migration changes the measured universe;
4. record the reason in the PR and this document when the baseline must increase for a legitimate migration reason;
5. never add a persistent workflow that automatically rewrites the baseline.

Temporary one-shot workflows used during the 2026-08-25 bootstrap were deleted before merge. The production foundation verifier explicitly forbids them from returning.

## Cleanup priority

Legacy debt should be reduced in risk order rather than by raw count:

1. React correctness rules: state mutation, render-time refs, invalid Hook patterns, unstable component creation;
2. auth, checkout, payment, payout, KYC, messaging and Admin route findings;
3. TypeScript `any` and unsafe narrowing in domain/API boundaries;
4. accessibility and image/navigation issues on customer-facing flows;
5. unused imports/variables and lower-risk style findings.

Every cleanup PR must still pass the normal fresh-Supabase, HTTP authorization, typecheck, build and deployment gates when its scope touches those surfaces.

## Exit condition

The long-term target is `npm run lint:strict` with zero errors and zero warnings. Until that point, the committed baseline is a transparent debt ceiling—not a waiver—and production CI prevents the debt from growing.
